01 / Motivation

The Assurance Gap in Traditional Software Testing

Traditional unit tests check only the edge cases you remember to write. Property-based testing goes further — but still hits a ceiling.

Limit 1 Unit Tests Miss Edge Cases

Example-based tests only verify scenarios you explicitly imagined. Subtle combinations and boundary bugs slip straight through.

Next Step Property-Based Testing

Tools like Hypothesis automatically generate thousands of inputs — let's look at how it works and where it still hits the Test Oracle Problem.

01b / Property-Based Testing

Meet Hypothesis: Property-Based Testing in Python

Instead of hand-writing fixed examples, declare input strategies and let Hypothesis hunt for edge cases automatically.

Hypothesis Quick Example 
from hypothesis import given, strategies as st

@given(xs=st.lists(st.integers()))
def test_sort_idempotent(xs):
    assert sorted(sorted(xs)) == sorted(xs)

Benefits Why Developers Love Hypothesis

  • Finds blind-spot edge cases: Automatically tries empty lists, duplicates, negative/huge numbers, and rare combinations.
  • Automatic Shrinking: Reduces noisy random failures into the smallest human-readable counterexample.
  • Regression Memory: Caches past failing inputs in .hypothesis/ and replays them first on future runs.

Downsides Where Hypothesis Alone Falls Short

  • The Test Oracle Problem: Generating inputs is easy, but checking exact outputs often forces you to re-implement the logic in tests.
  • Probabilistic, Not Exhaustive: Passing 500 random runs still cannot prove a bug doesn't exist in an untested corner.
  • Strategy Effort: Complex valid states require carefully written custom generators to avoid shallow or slow tests.
Bridge to Lean 4: Hypothesis excels at input generation & shrinking — Lean 4 fills its biggest gap by supplying a mathematically verified oracle.
01c / Closing the Gap

How Formal Verification Elevates Property-Based Testing

Adding a Lean 4 executable specification fills the upper-right gap — turning Hypothesis from guesswork into specification-backed testing.

Solved The Test Oracle Dilemma

Upgrade What Formal Verification Adds

  • Best of both worlds: Hypothesis explores deep runtime paths; Lean 4 guarantees the ground truth.

02 / Lean 4 Basics

What Makes Lean 4 Different from Older Proof Assistants?

Lean 4 unifies a dependently typed functional programming language, an interactive theorem prover, and a native C compiler.

Dual Nature Code + Proof Together

In Lean 4, functions and theorems live in the same language. There is no fragile "code extraction" step like in older theorem provers.

Modern Automation (2025–2026)

  • grind — SMT-style built-in tactic (congruence closure, E-matching, linear arithmetic).
  • bv_decide — SAT-backed bitvector & overflow proofs checked by the kernel.
  • Std.Do / mvcgen — Hoare-logic VC generation for do-notation code.
  • Plausible — Built-in QuickCheck-style counterexample finder.
02b / Lean 4 Basics

What Does It Mean to "Run" a Spec — and Why Native?

Turning a mathematical specification into a fast, standalone ground-truth calculator (Test Oracle).

1. Throughput Built for High-Volume Fuzzing

Proof terms exist only for the kernel and are erased at compile time. The remaining pure functions compile to fast C, enabling thousands of differential checks per second (or millions nightly).

2. Zero Extraction No Fragile Glue Layer

Older provers (Coq, Isabelle) required translating specs to OCaml/Haskell to run them. Lean 4 compiles your exact verified functions directly alongside Lean.Data.Json and IO.

3. Standalone Clean CI Integration

The output (tictactoe_oracle) is a self-contained binary. pytest calls it via subprocess.Popen without starting the Lean compiler or type-checker at test time.

02 / Lean 4 Basics

Essential Lean 4 Building Blocks in 60 Seconds

Just 5 keywords cover 90% of what you need to write executable software specifications.

Lean 4 Primer 
-- 1. Algebraic Data Type (Enum / Tagged Union)
inductive Player where
  | X | O
  deriving BEq, DecidableEq, Repr

-- 2. Record / Dataclass
structure GameState where
  board  : List (Option Player)
  turn   : Player
  status : GameStatus

-- 3. Pure Total Function (executable!)
def Player.other : Player → Player
  | .X => .O
  | .O => .X

-- 4. Theorem (checked by Lean kernel at build time)
theorem other_involutive (p : Player) :
    p.other.other = p := by
  cases p <;> rfl

-- 5. Elaboration-time assertion (fails build if false)
#guard Player.X.other == .O

inductive & structure

Define strict, exhaustive domain models. Illegal states (like a player other than X/O) become unrepresentable at compile time.

def & Except

Functions are pure by default. Instead of raising runtime exceptions, return Except String GameState so every error path is explicit.

theorem & #guard

theorem proves a property for all possible inputs. #guard runs concrete sanity checks during compilation (lake test).

Toolchain: Managed by elan + lake (similar to rustup + cargo or uv).
03 / Core Concept

Combining Lean 4 with Python: Verification-Guided Development

Don't try to formally verify dynamic Python code directly. Instead, prove the Lean 4 spec and lock Python to it via Differential Testing.

03b / Architecture Trade-off

Wait — Why Not Just Build the Whole App in Lean 4?

Lean 4 can build real programs (its own compiler is in Lean 4!), but separating Spec and Production App wins in practice.

1. Ecosystem Libraries & Cloud Integrations

Lean 4 shines in math & verification, not Web frameworks, Cloud SDKs, ORMs, or AI/ML stacks. Rebuilding that ecosystem wastes time.

2. Provable ≠ Fast Decouple Clarity from Speed

Simple pure code is easy to prove; cached/vectorized production code breaks proofs on every refactor. Keeping them separate lets both excel.

3. Team Reality No Rewrite Needed

Existing Python teams keep shipping normally while a small group (or AI agents) maintains the Lean 4 spec for critical invariants.

Exception: For tiny, pure, ultra-critical cores (e.g., policy engine or parser), compiling Lean 4 to a C ABI shared library and calling it via Python FFI is a viable option.
03c / Mapping Assurance

How Do We Know Python & Lean 4 Are Mapped Correctly?

There is no automatic compiler proof linking Python to Lean — instead, 4 engineering layers keep the mapping airtight.

Contract Lock the I/O Boundary

Even if Python uses loops and Lean uses foldlM, matching the exact JSON response & error strings guarantees black-box alignment.

Audit Coverage & Mutation Testing

Run pytest --cov to verify 100% Python branch coverage under differential tests, and use mutation testing (mutmut) to ensure no unmapped logic slips by.

Zero Drift CI Enforces Sync

Editing only Python or only Lean immediately turns CI red — preventing silent divergence between spec and production code.

Clean Division of Labor: Lean Proofs verify spec correctness; Differential + Mutation Testing verify Python↔Lean mapping.

Step 1 of 6 Production Python

Decouple Pure Business Logic from I/O

Keep the core rules pure and deterministic in tictactoe/game.py with a clean JSON-compatible contract.

tictactoe/game.py 
def apply_move(state: GameState, pos: int):
    if state.status != "ongoing":
        return None, "game_over"
    if pos < 0 or pos >= 9:
        return None, "out_of_bounds"
    if state.board[pos] is not None:
        return None, "cell_occupied"

    new_board = _place(state.board, pos, state.turn)
    if _has_won(new_board, state.turn):
        return GameState(new_board, state.turn, "won", state.turn), None
    if all(c is not None for c in new_board):
        return GameState(new_board, state.turn, "draw", None), None
    return GameState(new_board, _other(state.turn), "ongoing", None), None

def play_moves(moves: list[int]) -> dict:
    state = initial_state()
    for pos in moves:
        state, err = apply_move(state, pos)
        if err:
            return {"ok": False, "error": err}
    return state.to_dict()

Design Principle: Functional Core

  • Immutable state: @dataclass(frozen=True) with tuple board avoids mutation bugs.
  • Explicit error codes: Returning "game_over" / "out_of_bounds" / "cell_occupied" maps 1-to-1 to Lean's Except.
  • Replayable entrypoint: play_moves(moves) takes a plain list of ints — ideal for fuzzing!

Shared JSON Wire Contract

Success:

{"ok": true, "board": ["X", ...], "turn": "O", "status": "ongoing", "winner": null}

Error:

{"ok": false, "error": "cell_occupied"}

Step 2 of 6 Executable Specification

Modeling the Rules Cleanly in Spec.lean

The specification is short, declarative, and directly executable — serving as the single source of truth.

lean_spec/TicTacToe/Spec.lean 
inductive GameStatus where
  | ongoing | won (p : Player) | draw
  deriving BEq, DecidableEq, Repr

def applyMove (s : GameState) (pos : Nat)
    : Except String GameState :=
  if s.status != .ongoing then
    .error "game_over"
  else if pos ≥ 9 then
    .error "out_of_bounds"
  else if cellAt s.board pos != none then
    .error "cell_occupied"
  else
    let board' := s.board.set pos (some s.turn)
    if hasWon board' s.turn then
      .ok { board := board', turn := s.turn, status := .won s.turn }
    else if isFull board' then
      .ok { board := board', turn := s.turn, status := .draw }
    else
      .ok { board := board', turn := s.turn.other, status := .ongoing }

def playMoves (moves : List Nat) : Except String GameState :=
  moves.foldlM applyMove initialState
Step 3 of 6 Formal Proofs & Compile-Time Checks

Proving Spec Invariants in Proofs.lean

Before trusting the oracle, Lean's kernel mathematically verifies its properties during lake test.

lean_spec/TicTacToe/Proofs.lean 
-- 1. Universal Theorems (hold for ALL states & moves)
theorem applyMove_rejects_finished_game
    (s : GameState) (pos : Nat)
    (hdone : s.status ≠ .ongoing) :
    applyMove s pos = .error "game_over" := by
  unfold applyMove; simp [hdone]

theorem applyMove_rejects_out_of_bounds
    (s : GameState) (pos : Nat)
    (hongoing : s.status = .ongoing) (hge : pos ≥ 9) :
    applyMove s pos = .error "out_of_bounds" := by
  unfold applyMove; simp [hongoing, hge]

theorem applyMove_preserves_board_length ... :
    s'.board.length = s.board.length := ...

-- 2. Elaboration-time concrete assertions
#guard playMoves [0, 0] == .error "cell_occupied"
#guard playMoves [0, 3, 1, 4, 2, 5] == .error "game_over"

lakefile.toml Native lake test

Setting testDriver = "TicTacToe" turns library elaboration itself into a test runner: if any theorem proof breaks or any #guard evaluates to false, lake test exits non-zero.

What These Proofs Guarantee

  • Safety: A finished game can never accept another move.
  • Bounds: Coordinates ≥ 9 are always rejected cleanly.
  • Structural integrity: Board length stays invariant (9) across every valid transition.
Pro Tip: For complex specs, try by plausible first to falsify buggy theorems before spending time proving them!
Steps 4 & 5 of 6 Fast Bridge

Persistent JSON Lines Oracle (Main.lean + conftest.py)

Spawning a subprocess per test case is slow. A persistent stdin/stdout pipe achieves thousands of checks per second.

lean_spec/Main.lean (excerpt) 
partial def loop (stdin stdout : IO.FS.Stream) : IO Unit := do
  let line ← stdin.getLine
  if line.isEmpty then return ()
  let resp := match Json.parse line.trim >>= fromJson? with
    | .ok (req : PlayRequest) => resultToJson (playMoves req.moves)
    | .error err => ...
  stdout.putStrLn resp.compress
  stdout.flush   -- critical: prevents pipe deadlock!
  loop stdin stdout

Step 6 of 6 Differential Testing in Action

Catching Bugs Unit Tests Miss (test_differential.py)

Hypothesis explores both invalid/chaotic inputs and full legal games — then automatically shrinks any divergence to a minimal repro.

tests/test_differential.py 
# Strategy 1: Chaotic sequences (bounds, duplicates, post-win)
@settings(max_examples=500)
@given(moves=st.lists(
    st.integers(min_value=0, max_value=11),
    max_size=12,
))
def test_random_move_sequences_match_lean_spec(lean_oracle, moves):
    assert play_moves(moves) == lean_oracle.play(moves)

# Strategy 2: Permutations of 0..8 (deep wins & draws)
@settings(max_examples=500)
@given(moves=st.permutations(list(range(9))))
def test_full_game_permutations_match_lean_spec(lean_oracle, moves):
    for k in range(len(moves) + 1):
        seq = moves[:k]
        assert play_moves(seq) == lean_oracle.play(seq)

06 / Tooling Positioning

Hypothesis vs. Plausible: Where Does Each Fit?

Both are QuickCheck-style Property-Based Testing tools — but they test different layers at different stages.

Core in Sample Hypothesis (Python Side)

  • Target: Verifies that your Python production code matches the Lean 4 oracle.
  • When it runs: Every local run & CI pipeline (uv run pytest).
  • Role: The primary engine driving Differential Testing in this sample.

Optional Power-Up Plausible (Lean 4 Side)

  • Target: Checks whether your Lean 4 spec / theorem statement is actually true before investing time proving it.
  • Why omitted here: Intentionally excluded from our minimal Tic-Tac-Toe sample to keep zero external Lean dependencies.
  • When to add: Add via Lake once your domain specs & invariants grow complex.
