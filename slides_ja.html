01 / 背景・課題

従来のテストだけでは埋められない品質ギャップ

Unit Test は「思いついたケース」しか検証できず、Property-Based Testing へ進んでもまだ壁が残ります。

限界 1 Unit Test は想定外を見逃す

例題ベースのテストは開発者が意識したケースしか守れません。複雑な状態遷移や境界条件のバグがすり抜けます。

次の一手 Property-Based Testing

Hypothesis を使えば数千の入力を自動生成できます。まずはその仕組みと、残る課題（Test Oracle 問題）を見ていきましょう。

01b / Property-Based Testing 入門

Hypothesis とは？Python の Property-Based Testing

固定のテストケースを手書きする代わりに、入力の生成戦略 (Strategy) と満たすべき性質を宣言し、エッジケースを自動探索します。

Hypothesis の最小コード例 
from hypothesis import given, strategies as st

@given(xs=st.lists(st.integers()))
def test_sort_idempotent(xs):
    assert sorted(sorted(xs)) == sorted(xs)

メリット Hypothesis が強力な理由

  • 見落としがちな境界値を発見: 空配列・重複・極端な数値など、人間が思いつかない入力を自動で試す。
  • 自動 Shrinking: 複雑な失敗入力を、人間が原因を追いやすい最小の再現手順まで自動で縮小。
  • 回帰テストの記憶: 過去の失敗例を .hypothesis/ に保存し、次回から優先的に再検証。

弱点・限界 Hypothesis 単体の課題

  • Test Oracle 問題: 入力生成は簡単だが、「正確な期待出力」を判定するには結局テスト側にも仕様を書く必要がある。
  • 確率的であり網羅証明ではない: 500 回通っても、試していないコーナーケースにバグが残る可能性をゼロにはできない。
  • Strategy 設計コスト: 複雑なドメインでは有効な状態を作るカスタム generator の工夫が必要。
Lean 4 への橋渡し: 入力生成と shrinking は Hypothesis が最強。その最大の弱点である「Test Oracle 問題と数学的保証」を Lean 4 で補完します。

Lean 4 の実行可能な仕様を右上に配置することで、Hypothesis の弱点（Oracle 問題）を解消し、実務のスイートスポットに到達します。

解決 Test Oracle 問題からの解放

Python テスト側に期待値ロジックを重複実装する代わりに、数学的に証明済みの Lean 4 モデルと直接出力を突き合わせます。

進化 形式検証がもたらす価値

  • 仕様の確実性: 重要な不変条件をサンプリングではなく全入力 (∀) に対して証明。
  • バグの重複防止: 独立した簡潔なモデルが信頼できる正解になる。
  • いいとこ取り: 探索力は Hypothesis、正解の厳密さは Lean 4 が担当。

02 / Lean 4 の基礎

なぜ Lean 4 はソフトウェアテストに向いているのか？

Lean 4 は「依存型関数型言語」「定理証明支援系」「高速なネイティブ C コンパイラ」を 1 つに統合しています。

二面性 コードと証明を同じ言語で

従来の証明支援系のような煩雑なコード抽出が不要。書いた仕様がそのままネイティブバイナリとして高速に動きます。

2025〜2026 の最新自動化スタック

  • grind — SMT 着想の組み込み自動証明 tactic（等号・線形算術等）。
  • bv_decide — SAT ソルバ連携によるビット演算・オーバーフロー証明。
  • Std.Do / mvcgen — do 記法の命令的コードから Hoare 論理 VC を生成。
  • Plausible — QuickCheck 型の組み込み反例探索（PBT）。
02b / Lean 4 の基礎

仕様を「実行する」とは？なぜネイティブコンパイラが必要か

数学的な仕様を、入力を入れれば正解を返す超高速な「正解マシーン (Test Oracle)」に変える仕組みです。

1. 圧倒的高速性 大量 Fuzzing に耐える速度

証明にしか使わない情報（proof terms）はコンパイル時に消去され、純粋な計算だけが高速な C バイナリになります。AWS Cedar では 1 評価あたり数マイクロ秒で動作します。

2. コード抽出不要 変換ズレの罠がない

従来の証明支援系（Coq 等）は実行のために OCaml/Haskell へ変換が必要でした。Lean 4 は証明した関数そのものに Json や IO を付けて直接ビルドできます。

3. 単体実行 CI への組み込みがシンプル

ビルド済みの tictactoe_oracle は単体バイナリのため、テスト実行時に Lean 処理系を起動する必要がなく、pytest から普通の CLI として呼べます。

02 / Lean 4 の基礎

60 秒でわかる Lean 4 の 5 大構文

ソフトウェア仕様を書くのに必要な構文は、実質この 5 つだけで 9 割カバーできます。

Lean 4 クイックリファレンス 
-- 1. 代数的データ型 (Enum / Tagged Union)
inductive Player where
  | X | O
  deriving BEq, DecidableEq, Repr

-- 2. 構造体 (Python の dataclass 相当)
structure GameState where
  board  : List (Option Player)
  turn   : Player
  status : GameStatus

-- 3. 純粋な実行可能関数
def Player.other : Player → Player
  | .X => .O
  | .O => .X

-- 4. 定理（ビルド時に Lean kernel が厳密に検証）
theorem other_involutive (p : Player) :
    p.other.other = p := by
  cases p <;> rfl

-- 5. コンパイル時アサーション（偽ならビルド失敗）
#guard Player.X.other == .O

inductive & structure

ドメインモデルを厳密な型で定義。X / O 以外の不正なプレイヤーなど、あり得ない状態を型レベルで排除します。

def & Except

関数はデフォルトで純粋。例外を投げる代わりに Except String GameState を返し、エラー経路をすべて明示します。

theorem & #guard

theorem は全入力に対する普遍的性質を証明。#guard は具体例をコンパイル時に自動チェックします（lake test）。

ツールチェーン: elan + lake で管理（Rust の rustup + cargo、Python の uv に相当）。

Python × Lean 4: Verification-Guided Development

03b / アーキテクチャ判断

疑問：Lean 4 でそのままアプリ全体を書けばいいのでは？

技術的には可能（Lean 4 コンパイラ自身も Lean 4 製）ですが、実務では仕様と本番アプリを分離する方が合理的です。

1. エコシステム差 周辺ライブラリが不足

Web フレームワーク、Cloud SDK、DB、AI/ML スタックは Python 等が圧倒的に充実。Lean 4 で車輪の再発明をするのは非効率。

2. 証明しやすさ ≠ 速さ 関心事の分離

最適化された本番コードを直接証明するとリファクタのたびに証明が壊れます。明快な仕様と高速な実装を分けるのが定石（AWS Cedar も同様）。

3. 既存資産とチーム 書き直し不要

既存チームは普段どおり Python で開発を続けつつ、重要なコア仕様だけを少人数（または AI Agent）が Lean 4 で検証できます。

例外: 認可エンジンやパーサなど純粋計算だけの小さな超重要コアなら、Lean 4 を C 共有ライブラリ化して Python から FFI で直接本番利用する選択もアリです。
03c / マッピングの保証

Python と Lean 4 が正しく対応しているかどう確認する？

Python と Lean 間に自動証明はありませんが、4 層の防御でマッピングの正しさと同期を継続的に担保します。

境界契約 入出力を厳密に揃える

内部実装が違っても（Python の for vs Lean の foldlM）、JSON 構造とエラーコードの一致でブラックボックス等価性を検証。

穴の検査 カバレッジ & Mutation Test

pytest --cov で Python 全分岐の到達を確認し、mutmut 等でコードをわざと壊して Lean Oracle が全部検知できるか測る。

ドリフト防止 CI で片側変更をブロック

Python だけ／Lean だけ変更すると CI の Differential Test が即座に赤くなり、仕様と実装の乖離を構造的に防げる。

役割分担の完結: 「仕様の正しさ」＝ Lean の定理証明、「Python との対応」＝ Differential + カバレッジ / Mutation テスト。

Step 1 / 6 本番 Python 実装

純粋なビジネスロジックを I/O から切り離す

tictactoe/game.py に決定的な状態遷移関数をまとめ、JSON 互換の入出力契約を揃えます。

tictactoe/game.py 
def apply_move(state: GameState, pos: int):
    if state.status != "ongoing":
        return None, "game_over"
    if pos < 0 or pos >= 9:
        return None, "out_of_bounds"
    if state.board[pos] is not None:
        return None, "cell_occupied"

    new_board = _place(state.board, pos, state.turn)
    if _has_won(new_board, state.turn):
        return GameState(new_board, state.turn, "won", state.turn), None
    if all(c is not None for c in new_board):
        return GameState(new_board, state.turn, "draw", None), None
    return GameState(new_board, _other(state.turn), "ongoing", None), None

def play_moves(moves: list[int]) -> dict:
    state = initial_state()
    for pos in moves:
        state, err = apply_move(state, pos)
        if err:
            return {"ok": False, "error": err}
    return state.to_dict()

設計のポイント: Functional Core

  • 不変な状態: @dataclass(frozen=True) + tuple で副作用によるバグを防止。
  • 明示的なエラーコード: "game_over" / "out_of_bounds" / "cell_occupied" を Lean の Except と 1対1 対応させる。
  • リプレイ可能な入口: play_moves(moves) が整数リストを受け取るため、Fuzzing しやすい。

共通 JSON インターフェース

正常系:

{"ok": true, "board": ["X", ...], "turn": "O", "status": "ongoing", "winner": null}

エラー系:

{"ok": false, "error": "cell_occupied"}

Step 2 / 6 Executable Specification

Spec.lean でルールを簡潔にモデル化する

仕様書であると同時にそのまま実行できるコード（Single Source of Truth）を Lean 4 で書きます。

lean_spec/TicTacToe/Spec.lean 
inductive GameStatus where
  | ongoing | won (p : Player) | draw
  deriving BEq, DecidableEq, Repr

def applyMove (s : GameState) (pos : Nat)
    : Except String GameState :=
  if s.status != .ongoing then
    .error "game_over"
  else if pos ≥ 9 then
    .error "out_of_bounds"
  else if cellAt s.board pos != none then
    .error "cell_occupied"
  else
    let board' := s.board.set pos (some s.turn)
    if hasWon board' s.turn then
      .ok { board := board', turn := s.turn, status := .won s.turn }
    else if isFull board' then
      .ok { board := board', turn := s.turn, status := .draw }
    else
      .ok { board := board', turn := s.turn.other, status := .ongoing }

def playMoves (moves : List Nat) : Except String GameState :=
  moves.foldlM applyMove initialState
Step 3 / 6 形式証明 & コンパイル時テスト

Proofs.lean で仕様の不変条件を証明する

Oracle を信頼する根拠として、lake test 実行時に Lean kernel が重要な性質を数学的に検証します。

lean_spec/TicTacToe/Proofs.lean 
-- 1. 普遍的な定理（あり得るすべての盤面・手に対して成立）
theorem applyMove_rejects_finished_game
    (s : GameState) (pos : Nat)
    (hdone : s.status ≠ .ongoing) :
    applyMove s pos = .error "game_over" := by
  unfold applyMove; simp [hdone]

theorem applyMove_rejects_out_of_bounds
    (s : GameState) (pos : Nat)
    (hongoing : s.status = .ongoing) (hge : pos ≥ 9) :
    applyMove s pos = .error "out_of_bounds" := by
  unfold applyMove; simp [hongoing, hge]

theorem applyMove_preserves_board_length ... :
    s'.board.length = s.board.length := ...

-- 2. コンパイル時の具体例チェック (#guard)
#guard playMoves [0, 0] == .error "cell_occupied"
#guard playMoves [0, 3, 1, 4, 2, 5] == .error "game_over"

lakefile.toml ネイティブ lake test

testDriver = "TicTacToe" を設定すると、ライブラリの型チェック自体がテストになります。証明の破綻や #guard 失敗があれば lake test が即座に失敗します。

これらの証明が保証すること

  • 安全性: 終了済みゲームではどんな手も絶対に受け付けない。
  • 境界チェック: 9 以上の座標は必ず "out_of_bounds" で拒否。
  • 構造不変性: どの有効な遷移を経ても盤面長（9）は絶対に壊れない。
実践 Tips: 複雑な仕様では、証明に着手する前に by plausible で反例がないか先に確認すると手戻りを防げます。

Step 6 / 6 Differential Testing の威力

Unit Test をすり抜けるバグを自動検知 (test_differential.py)

Hypothesis が不正入力・全順列を網羅的に探索し、仕様とのズレを最小手順まで自動で shrinking します。

tests/test_differential.py 
# 戦略 1: 範囲外(9..11)・重複手・決着後の手を含むランダム列
@settings(max_examples=500)
@given(moves=st.lists(
    st.integers(min_value=0, max_value=11),
    max_size=12,
))
def test_random_move_sequences_match_lean_spec(lean_oracle, moves):
    assert play_moves(moves) == lean_oracle.play(moves)

# 戦略 2: 0..8 の順列で勝敗・引き分け・途中経過を全検証
@settings(max_examples=500)
@given(moves=st.permutations(list(range(9))))
def test_full_game_permutations_match_lean_spec(lean_oracle, moves):
    for k in range(len(moves) + 1):
        seq = moves[:k]
        assert play_moves(seq) == lean_oracle.play(seq)

06 / ツールの使い分け

補足：Hypothesis と Plausible の役割分担

どちらも QuickCheck 系の Property-Based Testing ですが、検証対象と使うフェーズが異なります。

サンプルの主役 Hypothesis（Python 側）

  • 対象: Python 本番実装が Lean 4 Oracle と一致しているかを検証。
  • 実行タイミング: 毎回のローカルテスト・CI（uv run pytest）。
  • 役割: 本サンプルにおける Differential Testing の中核エンジン。

任意の拡張 Plausible（Lean 4 側）

  • 対象: Lean 4 の仕様や定理の仮説自体にミスがないかを証明前に反例探索。
  • 今回未導入の理由: Tic-Tac-Toe 最小サンプルでは外部依存ゼロを優先して意図的に省略。
  • 導入の目安: 課金・認可など仕様が複雑になってきた段階で Lake に追加する。

JSON 契約の固定・Differential Testing・分岐カバレッジ 100% / Mutation Test・CI 強制でドリフトを防ぎます。

4 重要な 10〜20% から小さく始める

認可・課金・状態遷移など純粋ロジック層に絞り、残りの I/O 層は通常の pytest に任せるのが最短ルートです。
